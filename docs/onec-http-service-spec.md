# ТЗ: HTTP-сервис 1С для дашборда (черновик v2)

Статус: черновик для обсуждения с разработчиком 1С. Составлен по коду дашборда (`app/**`, `server/**`, `scripts/audit-onec.mjs`, `tests/**`) после просмотра **всех экранов**. Что в коде не подтвердилось, вынесено в раздел 8.

## 1. Зачем

Сейчас дашборд читает 1С через стандартный OData и считает всё в Node. Причины медленной работы:

1. **N+1 по справочникам.** 1С отвечает ошибкой 500 на фильтр с несколькими `Ref_Key` (комментарий в `server/index.mjs:507`), поэтому каждый товар, склад, магазин, продавец и подкатегория запрашиваются отдельным запросом `Catalog_X(guid'...')`, по 15 параллельно.
2. **Постраничное чтение документов.** `Document_ОтчетОРозничныхПродажах` по 25 штук за запрос, `Document_ЧекККМ` по 100–500 штук вместе с табличными частями, до 50 000 чеков.
3. **Сканирование без фильтра по дате.** Аналитика чеков за период читает заголовки чеков от «сейчас» назад (до 200 запросов).
4. **Повторные запросы.** Экран продаж вызывает `onec-reports` 3 раза (текущий период, предыдущий, справочники).
5. **Агрегация в Node.** Всё суммируется по сырым строкам на сервере дашборда.

Цель: один-два запроса на экран, готовые агрегаты, названия приходят вместе с данными.

## 2. Общие требования к сервису

- HTTP-сервис конфигурации, ответы `application/json; charset=utf-8`, версия в пути: `/dashboard/v1/...`.
- Basic-авторизация, отдельный пользователь только на чтение.
- Даты в параметрах `YYYY-MM-DD`, границы **включительно**: `from` с 00:00:00, `to` до 23:59:59 по времени магазина. Сейчас смещение берётся из `ONEC_TIMEZONE_OFFSET_MINUTES` (по умолчанию +6 ч), а интерфейс считает границы в часовом поясе браузера. В ответах даты в ISO 8601 со смещением либо дата дня в локальном времени магазина.
- Только проведённые (`Posted = true`) документы, без помеченных на удаление.
- Все фильтры (даты, магазин, канал) применяются в 1С.
- Ни одному ответу не должны требоваться дозапросы справочников по ключу: названия приходят в самих строках.
- В каждом ответе `meta`: `generatedAt`, `asOf`, `durationMs`, `latestDocumentDate` (дата последнего документа), `truncated`.
- Ошибки: код HTTP + `{ "message": "..." }`.
- Целевое время ответа: до 3 секунд на период до 90 дней (цифру согласовать, фактическое время сейчас не измерялось).

| Роль | Экран | Данные из 1С | Метод сервиса |
|---|---|---|---|

| manager | «Товары и продажи» | Те же + рейтинг товаров, ABC-анализ | 4.2, 4.3, 4.4, 4.5 |

Владелец по правам видит только отчёты, аналитику чеков, категории и маржу. Остальное для него закрыто на бэкенде дашборда.

## 4. Методы

### 4.1 `GET /stock`: остатки и складские операции (экран «Склад и остатки»)

Параметры: `date` (остатки на конец дня, по умолчанию сейчас), `from`, `to` (период для документов).

Нужно:

**а) Остатки** (строка = товар; если нужна разбивка по складам, то товар × склад, см. вопрос 1):

| Поле | Назначение в интерфейсе |
|---|---|
| `productKey`, `sku` (артикул, иначе код), `name` (полное наименование, иначе наименование) | Артикул, Товар |
| `category`, `group`, `subgroup` (+ ключи) | Фильтры, столбцы Категория и Подкатегория |
| `quantityWarehouse`, `quantityStore` | Остаток: склад, Остаток: магазин |
| `reserved` | Резерв |
| `warehouseNames` (список) | Расположение |

Тип помещения: `СкладскоеПомещение` → склад, `ТорговыйЗал` → магазин. Остальные типы нужно описать явно (сейчас они выпадают из обоих столбцов).

**б) Поступления** (заголовок + счётчики, без построчной детализации): `key`, `date`, `supplier`, `warehouse`, `warehouseKey`, `skuCount`, `units`. Нужно за период; сортировка от новых к старым. По ним строятся 8-недельный график и «Последние поставки» (5 штук).

**в) Списания**: `date`, `warehouseKey`, по строкам `sku`, `name`, `quantity`, `reason` (основание, иначе комментарий).

**г) Пересчёты**: `date`, `warehouseKey`, по строкам `sku`, `name`, `accounting` (учёт), `actual` (факт).

Правила, которые остаются в дашборде, а не в 1С: статус «мало» (доступно ≤ 5), рекомендация («Проверить закуп», «Дозаказать», «Высокий резерв» при резерве ≥ 50 %), «доступно = остаток − резерв, не меньше 0».

Себестоимость остатка (`ор_СебестоимостьBalance`) сейчас загружается, но нигде не показывается: можно не отдавать.

### 4.2 `GET /sales/daily`: динамика продаж (графики выручки, KPI)

Параметры: `from`, `to`, `compare` (`true` = вернуть ещё и предыдущий период той же длины, заканчивающийся днём раньше `from`), `granularity` (`day` | `hour`; `hour` нужен для режима «День»: график из 6 блоков по 4 часа), `storeKey`, `channel` (опционально, интерфейс продаж их пока не использует).

На каждый день (при `hour` на каждый час):

| Поле | Смысл |
|---|---|
| `date` (`hour`) | Период |
| `revenueNet` | Чистая выручка (после возвратов) |
| `returns` | Сумма возвратов |
| `revenueGross` | Продажи до возвратов |
| `unitsSold`, `unitsReturned` | Проданное и возвращённое количество |
| `documents` | Число документов (для проверки) |

Из этого интерфейс получает: чистую выручку за период, рост к предыдущему периоду, «последний день с продажами» и «предыдущий день с продажами» (для плашек «к предыдущему дню»), число проданных единиц, график с делением на 6/7/15/30 блоков. Сейчас блоки считаются на клиенте; можно оставить так.

### 4.3 `GET /sales/products`: продажи по товарам (категории, рейтинг, ABC)

Параметры: `from`, `to`.

На каждый товар, у которого за период есть движение: `productKey`, `sku`, `name`, `category`, `categoryKey`, `group`, `subgroup`, `subgroupKey`, `revenueNet` (Σ сумма продаж − Σ сумма возвратов), `unitsNet` (Σ продано − Σ возвращено).

Из этого строятся: «Продажи по категориям» с подкатегориями, «Топ товаров» и «Антитоп», таблица ABC (классы A ≤ 80 %, B ≤ 95 %, C остальное: пороги в дашборде), активные SKU (число различных товаров), CSV-выгрузки. Товары без движения за период не нужны.

Важно: доли категорий считаются от категоризированной выручки, а «Не классифицировано» в экране продаж отбрасывается, а в обзоре владельца показывается. Нужно решить, как единообразно отдавать категорию товаров без вида (см. вопрос 2).

### 4.4 `GET /checks`: аналитика чеков

Параметры: `from`, `to`, `includePrevious` (по умолчанию `false`; интерфейс всегда шлёт `false`).

Сводка периода:

| Поле | Смысл |
|---|---|
| `totalChecks` | Все чеки (продажи + возвраты) |
| `checks` | Чеки продаж |
| `returns`, `returnsAmount` | Число и сумма чеков возврата |
| `revenue` | Сумма чеков продаж без возвратов |
| `netRevenue` | Продажи минус возвраты |
| `averageCheck` | `revenue / checks` |
| `discounts` | Сумма скидок (автоматическая + ручная + оплата бонусами) |
| `grossRevenue` | Сумма товаров **до скидок** |
| `discountShare` | `discounts / grossRevenue × 100` |
| `certificatePayments`, `certificatesUsed` | Оплата сертификатами (сумма и число погашений) |
| `dataAvailable`, `documentDetailsAvailable`, `seriesAvailable` | Признаки полноты данных |

Серия для графика «Динамика количества чеков»: `label`, `checks`, `averageCheck` на каждый блок (для 1 дня 6 блоков по 4 часа, иначе по дням). Формат `label` должен быть оговорён.

Правила (уже реализованы в `server/dashboard/checks.mjs`, нужно перенести в 1С один в один): возврат — вид операции содержит «возврат»; аннулированные и отложенные чеки исключаются; сертификат определяется по виду оплаты со словом «сертификат».

Внимание: поле `grossRevenue` в чеках означает «до скидок», а в расчёте выручки по документам «продажи до возвратов». Лучше назвать по-разному (`revenueBeforeDiscount` для чеков).

В интерфейсе есть сверка «чеки против розничного отчёта» (расхождение больше 0,5 показывается предупреждением): значит, оба источника должны давать одинаковую чистую выручку.

### 4.5 `GET /margin`: маржа

Параметры: `from`, `to`, `storeKey` (guid или `all`), `channel` (`all` | `online` | `offline`), `includePrevious` (для экранов продаж и владельца `false`; в карточке «Маржа» экрана продаж есть дельта «п.п.» к прошлому периоду, но с `false` она не показывается).

Ответ: `current` (и `previous` при `includePrevious=true`): `revenue`, `revenueBeforeDiscount`, `cost`, `discounts`, `profit`, `marginPercent`, `efficiencyPercent`, `dataAvailable`.

Формулы (сейчас считаются в `server/dashboard/margin.mjs`): `discounts = max(revenueBeforeDiscount − revenue, 0)`, `profit = revenue − cost`, `marginPercent = profit / revenue × 100`, `efficiencyPercent = profit / cost × 100`. `dataAvailable = true`, если выручка нулевая или хотя бы по одной строке есть себестоимость; при нулевой себестоимости маржу не показывать (а не 100 %).

Нужен **единый источник себестоимости**. Сейчас в коде каскад: оборотный регистр продаж с `ор_Себестоимость` → документы продаж → срез `СебестоимостьНоменклатуры` × количество → сырой скан регистра.

### 4.6 `GET /sellers`: продажи по продавцам (экран «Продавцы»)

Параметры: `from`, `to`, `storeKey` (guid или `all`), `channel`.

Фильтр по магазину нужно выполнять **в 1С**: сейчас он делается на клиенте, и по нему же считаются уникальные чеки команды.

Строка = продавец × магазин:

| Поле | Смысл |
|---|---|
| `sellerKey`, `seller` | Продавец (физлицо) |
| `storeKey`, `store` | Магазин (если в строке не указан, то магазин продавца по умолчанию) |
| `revenue` | Чистая выручка (продажи минус возвраты) |
| `units` | Количество (с учётом возвратов) |
| `checks` | Число уникальных чеков продаж (возвраты не считаются) |
| `discounts` | Сумма скидок, не меньше 0 |
| `salesByDate` | `{ "YYYY-MM-DD": чистая сумма за день }` |

И итог по команде за те же фильтры: `teamRevenue`, `teamUnits`, `teamChecks` (**уникальные** чеки, один чек с несколькими продавцами считается один раз), `stores[]` с названиями. Список магазинов для фильтра должен быть полным, а не только с продажами в периоде.

Правила: продавец берётся со строки товара, при отсутствии — с документа; канал `online`, если заполнен `ЗаказПокупателя`, иначе `offline`; возвраты вычитаются.

Источник сейчас: `Document_ЧекККМ.Товары.Продавец_Key`, при отсутствии чеков — розничные отчёты. Подтвердить, что это верный источник «консультанта» (вопрос 6).

### 4.7 `GET /catalogs`: справочники (для фильтров)

Полные списки без привязки к продажам:
- **Магазины**: `key`, `name`, `code`.
- **Продавцы**: `key`, `name`, `defaultStoreKey`.
- **Склады**: `key`, `name`, `code`, `type` (`СкладскоеПомещение` / `ТорговыйЗал` / ...), `storeKey`.
- **Категории**: `key`, `name`. Сейчас в дашборде это 4 жёстко заданных значения (Домашний текстиль, Посуда, Одежда, Бытовая химия), определяемых по названию вида номенклатуры. С картинки: 5 типов, 19 групп (без корзины), 82 подгруппы, значит, нужно описать реальную иерархию.

## 6. Что остаётся локально в дашборде (не из 1С)

- Пользователи, сессии, роли (`data/auth.sqlite`).
- **План продаж команды** (`team_sales_plans`: магазин, период 1/7/30, канал, сумма). Ключ магазина — `Ref_Key` из 1С. Если в 1С есть документ планирования, его можно подтянуть (вопрос 7), иначе остаётся локально.
- Пороги и правила отображения: «мало» ≤ 5, резерв ≥ 50 %, ABC 80/95, предупреждение по скидкам > 10 %, актуальность данных 36 ч.
