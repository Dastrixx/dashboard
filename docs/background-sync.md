# Фоновая синхронизация исходных данных 1С

На этом этапе PostgreSQL хранит документы `Document_ОтчетОРозничныхПродажах` и их строки. Отдельный worker последовательно загружает дни из 1С, сохраняет покрытие и задачи в БД. `GET /api/dashboard/onec-reports?from=...&to=...&references=false` читает локальную БД при `SYNC_REPORTS_FROM_DB=true`. Пока нет ни одного готового дня, он возвращает HTTP 202, а React повторяет запрос каждые 3 секунды. Как только хотя бы один день готов, API отдаёт HTTP 200 с документами этих дней и полями `status`, `completedDays`, `totalDays`, `missingRanges` и `failedRanges`; экран показывает неполный период и обновляется до завершения. Если часть дней не удалась, готовая часть остаётся видимой с сообщением об ошибке. Когда не готов ни один день и задание завершилось неудачно, возвращается 503 с кнопкой «Повторить».

Worker также хранит исходные записи чеков, кассовых смен, поступлений, списаний, пересчётов, реализаций, заказов и перемещений, возвратов, регистров продаж, премий, остатков, цен и себестоимости, девяти справочников, снимки остатков и себестоимости в `onec_raw_records`. Каждая сущность имеет отдельное состояние в `sync_days` и `sync_jobs`; ошибки загрузки одной сущности не скрываются успешным состоянием отчётов. `sync:initial`, `sync:daily` и `sync:range` ставят все эти источники; только локальную фикстуру запускайте с `--reports-only`. Проверка покрытия: `npm run sync:raw-status -- --from=2026-09-01 --to=2026-09-28` (код выхода 1, пока что-то не готово).

При `SYNC_REPORTS_FROM_DB=true` активные маршруты панели читают PostgreSQL:

| Раздел | Источники |
| --- | --- |
| Динамика, рейтинг товаров, ABC, категории | Розничные отчёты и снимки справочников номенклатуры, видов и складов |
| Чеки и средний чек | `Document_ЧекККМ` и виды оплат |
| Продавцы | Строки чеков, при отсутствии консультантов — строки розничных отчётов; справочники физических лиц и магазинов |
| Маржа | Исходные движения `AccumulationRegister_Продажи_RecordType` |
| Склад и закуп / перемещение | Снимок остатков, документы поступления, списания и пересчёта, розничные отчёты и справочники |

Маршруты показывают уже завершённые дни и возвращают статус `syncing`, пока worker дочитывает период. Если источник завершается ошибкой, ранее полученные дни остаются доступны. Раздел закупа показывает рекомендации по правилу «доступно меньше проданного за период» и порогу 50%; он не создаёт документы в 1С. Расчёты маржи по исходным движениям и состав чеков требуют сверки с реальной базой перед использованием цифр для решений. Старые вспомогательные маршруты `/api/dashboard/onec-sellers` и `/api/dashboard/onec-product-categories` остаются прямыми запросами к 1С; интерфейс их не вызывает.

Чтение сохранённого источника (после авторизации владельца): `GET /api/sync/raw?source=Document_ЧекККМ&from=2026-09-01&to=2026-09-28&limit=100&offset=0`. Ответ содержит `items`, `total` и `meta`, на отсутствующий период возвращает 202 и ставит в очередь все источники, при неудачной загрузке возвращает 503. Данные каталога доступны за дату снимка (`from=to`). В выгрузке используются все свойства и табличные части, полученные OData, без пересчёта финансовых показателей.

В production включайте `SYNC_REPORTS_FROM_DB=true` после миграции и запуска worker. До появления завершённых дней соответствующие блоки ждут загрузки; при `SYNC_REPORTS_FROM_DB=false` остаётся прежний прямой путь к 1С. После включения проверьте ответы всех активных маршрутов на реальных сентябрьских данных и отдельно сверьте августовские чеки (ожидается не менее 6000 по данным пользователя).

## Проверка на Windows с реальной 1С

Используйте существующие значения `ONEC_ODATA_URL`, `ONEC_USER`, `ONEC_PASSWORD` в `.env` и запущенный Docker Desktop. Не запускайте `dev:mock-onec`. Рекомендуемые значения: `SYNC_ONEC_PAGE_SIZE=50`, `SYNC_REPORTS_FROM_DB=true`, `SYNC_TIMEZONE=Asia/Almaty`. Node.js должен соответствовать `engines.node` в `package.json` (не ниже 22.13).

```powershell
docker compose -f compose.sync.yaml up -d
npm ci
npm run db:migrate:sync
npm run sync:initial
```

Откройте три терминала: `npm run sync:worker`, `npm run dev:full` и `npm run sync:raw-status -- --from=2026-09-01 --to=2026-09-28`. У последней команды код выхода 1 ожидаем до завершения всех источников. Сначала должны стать доступны отчёты, затем справочники и снимок остатков, потом чеки, движения продаж и прочие документы. Если worker долго работает, он сообщает источник, страницу и время ожидания. Остановите старый worker перед запуском обновлённой версии: для одной базы разрешён один процесс.

Для диагностики откройте в панели сентябрьские «Продажи», «Склад», «Продавцы» и «Закуп / Перемещение». Результат `sync:raw-status` показывает покрытие по каждому источнику; `reports 28/28` подтверждает только розничные отчёты. Если источник не прошёл четыре попытки, смотрите `error=` в этом выводе и повторно поставьте диапазон через `npm run sync:range -- --from=2026-09-01 --to=2026-09-28 --retry-now`. Цифры по чекам, марже и остаткам пока не сверены с реальной 1С в среде разработки; локальные unit tests не заменяют эту проверку.

## Установка на Ubuntu/VDS

```bash
sudo apt update
sudo apt install -y postgresql postgresql-contrib
sudo -u postgres createuser --pwprompt dashboard
sudo -u postgres createdb --owner=dashboard dashboard
cd /path/to/dashboard
npm ci
```

В `.env` добавьте `DATABASE_URL=postgres://dashboard:<password>@127.0.0.1:5432/dashboard`, `SYNC_TIMEZONE=Asia/Almaty`, существующие `ONEC_*`. Пароль с символами `@`, `:` или `/` закодируйте как URL component. Миграция идемпотентна:

```bash
npm run db:migrate:sync
npm run sync:initial
pm2 start ecosystem.sync.config.cjs
pm2 save
```

`sync:initial` ставит в очередь текущий календарный месяц с первого числа по сегодня (например, 1–28 сентября). Worker сначала берёт задачи текущего месяца, затем, когда весь месяц до сегодняшнего дня готов, ставит в очередь три предыдущих месяца для фоновой загрузки. Задачи остаются в PostgreSQL после рестарта. Одновременно работает один worker: он удерживает PostgreSQL advisory lock, следующий процесс не начнёт параллельную загрузку. Worker каждый день после 05:00 `Asia/Almaty` ставит на повторную загрузку последние восемь календарных дат, включая сегодня. Отдельный системный cron не требуется. Явно запрошенный пользователем диапазон вне этих месяцев по-прежнему можно добавить через `sync:range`.

Если прежняя версия уже поставила в очередь несколько месяцев и нужно начать с сентября, остановите worker (он завершит текущий день) и выполните `npm run sync:prune-queue -- --from=2026-09-01 --to=2026-09-28`. Команда удаляет только ожидающие и неудачные задания вне выбранного диапазона; завершённые документы в БД сохраняются. Затем выполните `npm run sync:initial` и запустите worker снова. После готовности сентября он сам добавит три предыдущих месяца. Не задавайте `SYNC_AUTO_SCHEDULE=false`, если нужна фоновая загрузка.

Для проверки строго одного периода (например, августа) укажите в локальном `.env` `SYNC_AUTO_SCHEDULE=false`, остановите worker и запустите `npm run sync:prune-queue -- --from=2026-08-01 --to=2026-08-31`. Это удалит только ожидающие/неудачные задания вне августа. Затем `npm run sync:range -- --from=2026-08-01 --to=2026-08-31` и `npm run sync:worker`. Завершённые данные других месяцев сохраняются; автоматическое ежедневное расписание возобновится после удаления `SYNC_AUTO_SCHEDULE=false` и рестарта worker.

Ручная постановка диапазона:

```bash
npm run sync:range -- --from=2026-08-01 --to=2026-08-31
npm run sync:range -- --from=2026-08-01 --to=2026-08-31 --refresh
npm run sync:daily
pm2 logs dashboard-sync-worker --lines 100
```

`sync:range` переоткрывает только отсутствующие и неудачные дни; `sync:daily` обновляет готовые дни. Worker запрашивает документы целыми днями, страницами по 50, с ограничением времени из `ONEC_TIMEOUT_MS`; нагрузка на 1С последовательная. При успешной транзакции он заменяет полный набор за день, включая отменённые и удалённые документы. API показывает только `Posted=true` и `DeletionMark=false`. Если документ перенесён на другой день, он удаляется по `source_id` при обработке нового дня. Для старой даты вне rolling window потребуется `sync:daily` для затронутого дня или отдельная команда обновления диапазона.

Если конкретная база 1С запрещает фильтр `Date` в OData, worker пробует ограниченное постраничное чтение и отбирает нужный месяц локально. При стабильной сортировке по возрастанию он находит начало месяца через `$skip` и пропускает старые страницы; если 1С игнорирует `$orderby=Date desc`, это ускоряет первый проход. В логах выводятся источник, число пропущенных записей, каждая десятая страница и сообщение о работе каждые 30 секунд. При смене направления или превышении лимита страниц день остаётся несинхронизированным. Для больших источников размер страницы не опускается ниже 25, даже если старый локальный `.env` содержит `SYNC_ONEC_PAGE_SIZE=1`; рекомендуем установить `SYNC_ONEC_PAGE_SIZE=50`. После изменения конфигурации источника `sync:range -- --from=... --to=... --retry-now` немедленно переоткрывает ожидающие задания без вмешательства в выполняющееся задание.

Для реальной 1С используйте фактические `ONEC_ODATA_URL`, `ONEC_USER`, `ONEC_PASSWORD` (локальный порт может вести к прокси 1С). Не берите тестовые `mock` credentials из `.env.sync.local.example`. Перед загрузкой проверьте ответ 1С: `npm run sync:probe -- --from=2026-08-01 --to=2026-08-02`. Команда показывает путь источника и даты десяти документов без пароля, а также предупреждает, если 1С проигнорировала `$orderby=Date desc`. При возрастании дат первая страница не показывает самые новые отчёты. `sync:verify` сверяет только одну сущность отчётов; совпадение `0/0/0/0` не подтверждает наличие чеков или полноту всей панели.

## Проверка и включение для одного маршрута

Авторизуйтесь в панели и сохраните cookie сессии в файл, например `curl -c /tmp/dashboard.cookies -X POST .../api/auth/login ...`. Не записывайте cookie в репозиторий. Затем:

```bash
curl -b /tmp/dashboard.cookies 'http://127.0.0.1:4000/api/sync/health'
curl -b /tmp/dashboard.cookies 'http://127.0.0.1:4000/api/sync/status?from=2026-08-01&to=2026-08-31'
```

Дождитесь `ready` для тестового диапазона, сверьте число документов, сумму и строковые позиции с 1С. Только после сверки временно включите `SYNC_REPORTS_FROM_DB=true` в `.env` и перезапустите API через `pm2 restart dashboard-api --update-env`; сборка React не нужна. Проверка:

```bash
curl -i -b /tmp/dashboard.cookies 'http://127.0.0.1:4000/api/dashboard/onec-reports?from=2026-08-01&to=2026-08-31&references=false'
curl -i -b /tmp/dashboard.cookies 'http://127.0.0.1:4000/api/dashboard/onec-reports?from=2026-03-01&to=2026-03-31&references=false'
```

Первый запрос должен вернуть 200 из PostgreSQL, второй — 202 и поставить фоновую задачу. При недоступности 1С уже готовые дни читаются из БД, но остальные endpoints первого этапа зависят от 1С. После изменений кода: `npm ci && npm run build && pm2 restart dashboard-api dashboard-web dashboard-sync-worker --update-env`.

Rollback: верните `SYNC_REPORTS_FROM_DB=false`, выполните `pm2 restart dashboard-api --update-env`. Очередь и таблицы можно оставить; старый API маршрут продолжит использовать прежнюю логику. Не удаляйте данные PostgreSQL, пока не завершена сверка.
