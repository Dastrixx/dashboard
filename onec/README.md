# HTTP-сервис 1С для дашборда

Код для конфигуратора 1С. Заменяет OData-запросы дашборда на готовые JSON-ответы (см. `docs/onec-http-service-spec.md`).

Статус: **черновик методов `/v1/ping` и `/v1/stock`, в самой 1С не проверялся.** Код написан по именам объектов из OData-запросов дашборда, часть имён нужно сверить с конфигурацией (раздел «Что проверить»).

## Правило

Сначала проверяем на **локальной копии** базы (выгрузка `.dt`), и только потом переносим на рабочую базу, и там **в виде расширения конфигурации**, а не правкой основной конфигурации. Расширение не затрагивает поддержку типовой конфигурации и отключается одним действием.

## Шаг 1. Локальная копия (для проверки)

1. Администратор выгружает рабочую базу: Конфигуратор → «Администрирование» → «Выгрузить информационную базу…» → файл `.dt`. Выгрузка ничего в базе не меняет.
2. В запуске 1С: «Добавить» → «Создание новой информационной базы» → «Создание информационной базы без конфигурации» → имя `DashTest`, расположение «На данном компьютере».
3. Откройте её в конфигураторе: «Администрирование» → «Загрузить информационную базу…» → `.dt`.

## Шаг 2. Создать расширение с HTTP-сервисом

1. Конфигуратор → «Конфигурация» → «Расширения конфигурации» → «Добавить» → имя `ДашбордAPI`, синоним «Дашборд API».
   - Снимите флаги «Безопасный режим» и «Защита от опасных действий» только если они мешают запуску (для чтения данных обычно не мешают).
2. В дереве расширения: «Общие → HTTP-сервисы → Добавить».
   - Имя: `ДашбордAPI`
   - Корневой URL: `dashboard`
3. Шаблоны URL и методы:

   | Шаблон | Имя шаблона | HTTP-метод | Обработчик |
   |---|---|---|---|
   | `/v1/ping` | `Пинг` | GET | `ПингGET` |
   | `/v1/stock` | `Остатки` | GET | `ОстаткиGET` |

4. Вставьте содержимое `onec/DashboardAPI/Module.bsl` в модуль сервиса.
5. **Роль.** Создайте в расширении роль `ДашбордAPI_Доступ` с правом «Использование» на HTTP-сервис `ДашбордAPI` (только оно). Права на данные не нужны: модуль работает в привилегированном режиме и только читает.
6. Создайте отдельного пользователя (например, `dashboard.api`) только с этой ролью и режимом аутентификации «Аутентификация 1С:Предприятия». Личные учётные записи для дашборда не использовать.
7. Проверьте синтаксис: «Конфигурация» → «Проверка конфигурации» → «Синтаксический контроль модулей».

## Шаг 3. Проверить запросы без публикации

Откройте консоль запросов (или внешнюю обработку) на копии и выполните запросы из `Module.bsl` по очереди. Нужно, чтобы не было ошибок в именах реквизитов и ресурсов (раздел «Что проверить»).

## Шаг 4. Опубликовать

«Администрирование» → «Публикация на веб-сервере…» (нужен IIS или Apache, запуск от администратора). Отметьте «Публиковать HTTP-сервисы по умолчанию» либо включите именно `ДашбордAPI`.

Для рабочей базы публикация уже есть, нужно, чтобы в ней были разрешены HTTP-сервисы (в `default.vrd` элемент `httpServices`).

## Проверка

```bash
# Связка и авторизация
curl -u ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ "http://СЕРВЕР/ИМЯ_ПУБЛИКАЦИИ/hs/dashboard/v1/ping"

# Остатки на текущий момент + последние документы
curl -u ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ "http://СЕРВЕР/ИМЯ_ПУБЛИКАЦИИ/hs/dashboard/v1/stock"

# Остатки на дату и документы за период
curl -u ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ "http://СЕРВЕР/ИМЯ_ПУБЛИКАЦИИ/hs/dashboard/v1/stock?date=2026-10-20&from=2026-10-01&to=2026-10-27"
```

Адрес имеет вид `.../hs/<корневой URL>/<шаблон>`; `hs` добавляет платформа.

## Шаг 5. Перенос на рабочую базу

Только после успешной проверки на копии. Расширение загружается в рабочую базу администратором: «Конфигурация» → «Расширения конфигурации» → «Добавить» → загрузить файл `.cfe` (выгружается из копии). Затем «Обновить конфигурацию базы данных». Если расширение пойдёт не так, его отключают флажком «Активно».

## Что отдаёт `/v1/stock`

- `items[]`: остатки по связке товар × склад (`productKey`, `warehouseKey`, `quantity`, `reserved`).
- `products[]`: товары из ответа с названием, артикулом, категорией, группой и подгруппой (без дозапросов по ключу).
- `warehouses[]`: все склады с типом `store` (торговый зал), `warehouse` (складское помещение) или `other`.
- `categories[]`: категории и их алиасы.
- `receipts[]`: поступления (заголовок + число SKU и единиц). `writeOffs[]`, `recounts[]`: построчно.
- `meta`: `asOf`, период, `documentsLimited` (`true`, если период не задан и отданы только последние документы), `durationMs`.

Только проведённые документы. Даты в локальном времени базы, без смещения часового пояса.

## Что проверить на реальной базе

1. **Имена объектов и реквизитов**: `РегистрНакопления.ТоварыНаСкладах` (ресурсы `Количество`, `Резерв`), `Склады.ТипСклада`, `Склады.Магазин`, `Номенклатура.Артикул`, `НаименованиеПолное`, `ВидНоменклатуры`, `Документ.СписаниеТоваров.ОснованиеСписания`, `Документ.ПересчетТоваров.КоличествоФакт`.
2. **Остатки на текущий момент**: параметр `Граница = Неопределено` в виртуальной таблице должен вернуть последние остатки.
3. **Тип склада**: имя значения берётся через `ПолучитьПолноеИмяПредопределенногоЗначения`; если реквизит строковый, используется как есть. Проверьте `warehouses[].typeName`.
4. **Группа и подгруппа**: подгруппа — родитель товара, группа — родитель подгруппы. Это предположение (пункт 1 списка правок).
5. **Объём и время**: число строк в `items` и `meta.durationMs`.
